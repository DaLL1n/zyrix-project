# Структура проекта (Feature-Sliced Design)

Соблюдай строгую архитектуру FSD. Исходный код находится в `src/`.

- `app/` — Инициализация приложения, роутинг Next.js, глобальные провайдеры, layout.
- `views/` — Композиция целых страниц (замена слоя pages).
- `widgets/` — Самостоятельные и переиспользуемые блоки (Header, Footer).
- `features/` — Пользовательские сценарии, приносящие бизнес-ценность (Auth, ModalSearch).
- `entities/` — Бизнес-сущности без привязки к конкретным сценариям (Coin).
- `shared/` — Переиспользуемый инфраструктурный код, UI-кит, baseApi, утилиты.

**Правила слоев (КРИТИЧНО):**

- Модули должны импортировать зависимости ИСКЛЮЧИТЕЛЬНО из нижележащих слоев (app -> views -> widgets -> features -> entities -> shared).
- Кросс-импорты между модулями одного слоя (например, `features/auth` -> `features/modal-search`) СТРОГО ЗАПРЕЩЕНЫ.
- Для импортов из директории `src/` ВСЕГДА используй абсолютные пути с алиасом `@/` (например, `@/shared/ui/Button`). Использование относительных путей (`../../`) для кросс-слойных импортов запрещено.

# Архитектурные решения

- **Next.js:** Разделяй Server и Client Components. По умолчанию все компоненты — React Server Components (RSC). Директиву `"use client"` добавляй ТОЛЬКО в конечные узлы (листья) дерева компонентов, где напрямую используются хуки React (`useState`, `useEffect`), слушатели событий браузера или Redux-хуки.
- **RTK Query:** Основа API находится в `@/shared/api/baseApi.ts`. Фичи и сущности ДОЛЖНЫ расширять API через `injectEndpoints` в своих файлах. Явные интерфейсы для Request и Response обязательны (использование `any`/`unknown` запрещено). Настройка тегов (`providesTags`, `invalidatesTags`) для инвалидации кеша обязательна при добавлении мутаций.
- **Supabase:** Используй `@supabase/ssr` для работы на сервере (Server Actions, Route Handlers, RSC). Выполнение запросов к БД напрямую из клиентских компонентов ЗАПРЕЩЕНО — все данные должны загружаться на сервере и передаваться через пропсы, либо запрашиваться через RTK Query/Route Handlers.

# Строгие правила написания кода

- **TypeScript:** Строгий режим (`strict: true`). Использование `any` ЗАПРЕЩЕНО. Использование `as` (Type Assertion) ЗАПРЕЩЕНО, кроме случаев взаимодействия с нетипизированными внешними библиотеками (требует комментария `// Reason: ` с объяснением).
- **Декларативность:** Пиши чистые функции. Переопределение входных аргументов и прямая мутация объектов/массивов вне Redux Toolkit ЗАПРЕЩЕНЫ (используй spread или методы, возвращающие новые структуры).
- **Валидация (Zod):** Все внешние данные (ответы API, payload вебхуков, формы, параметры URL) ДОЛЖНЫ парситься через `schema.parse()` или `schema.safeParse()`. Слепая вера ответам API запрещена.
- **Именование:**
  - Компоненты, интерфейсы и типы — `PascalCase`.
  - Функции, переменные, хуки — `camelCase`.
  - Обработчики событий — префикс `handle` (например, `handleSubmit`).
  - Пропсы, принимающие обработчики — префикс `on` (например, `onSubmit`).
  - Zod-схемы — суффикс `Schema` (например, `userSchema`).
- **Стилизация:** Инкапсулируй стили. Используй ИСКЛЮЧИТЕЛЬНО SCSS Modules (`*.module.scss`). Для динамического объединения классов всегда используй утилиту `clsx`.
- **Ошибки:** Кастомный код, потенциально выбрасывающий исключения (fetch, парсинг, базы данных), должен быть обернут в `try/catch`. Перехватываемая ошибка должна быть типизирована перед использованием: `if (error instanceof Error)`. Пустые блоки `catch {}` ЗАПРЕЩЕНЫ.

# Безопасность

- **Никогда** не пиши в коде секреты, API-ключи, адреса БД, токены.
- Ключи окружения на клиенте (`NEXT_PUBLIC_*`) не должны содержать приватных токенов. Доступ к ним должен осуществляться через централизованный файл конфигурации с валидацией (Zod).
- Supabase RLS: При создании новых таблиц RLS должен быть явным образом включен (`ALTER TABLE ... ENABLE ROW LEVEL SECURITY;`), а политики доступа (Policies) написаны для SELECT, INSERT, UPDATE, DELETE.
